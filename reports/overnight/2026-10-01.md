## Code Review — Shortcomings & Issues

Prioritised per ponytail: redundancy, over-engineering, reinvented wheels.

**1. Raw CV JSONs committed past `.gitignore`, redundant with the repo's own aggregation path**
`models/slot/cv_results_xgb_handcrafted_sparse_esmc_win_*_pca9_*.json` (5b1a215), 4 × ~1.86 MB ≈ 7.4 MB of JSON. The repo's established convention is aggregate TSVs under `results/tables/`, and `src/pipeline/python/extract_model_metrics.py` already reduces exactly these JSONs to ~KB-scale tables. The only novel payload — per-fold predictions — lacks row identifiers, so even for the stated padding-subset purpose the files are unusable without re-deriving the fold split from `random_state=42` and df row order. Lazy fix: run the existing extractor and commit the TSV; leave raw JSONs on the cluster.
Severity: maintainability. Commit: 5b1a215.

**2. The stated "padding_subset" check has no artifact in the repository**
The commit message is the sole record; `git grep -i "padding_subset\|pad_subset"` over all tracked files returns nothing — no code, table, or note. A thesis reader cannot see what was checked, on which rows, or what it showed.
Severity: risk (evidence absent for a stated analysis step). Commit: 5b1a215.

**3. Provenance mismatch: committed runs contain features the committed pipeline does not produce**
Each JSON's `config.feature_names` includes `n_flank_len_real`, `c_flank_len_real`, `n_pad_len`, `c_pad_len` (plus `n_pad`/`c_pad`). The committed Python pipeline derives only `n_pad`/`c_pad` (`src/pipeline/python/04_modelling.py:1155-1160`), and the locally available split data (`data/processed/df_all_with_folds.csv`) contains none of the six columns (it has `start`/`end`/`protein_length`/`nflank_start`/…). The R pipeline computes flank lengths (`src/pipeline/r/functions.R:448-461`, `05_protein_features.R:75-76`) but downstream steps drop them (`06_netsurfp_protein_features.R:122`). So the code/data state that produced these runs is not fully in the repo.
Severity: risk (reproducibility). `# ponytail: no feature-provenance system needed — document the data/code version used for the 20260929 runs in the commit or thesis methods.` Commit: 5b1a215.

**4. Component composition drift between baselines and window runs (question for the authors, not a unilateral defect)**
Baseline rows report `handcrafted`=52 features; the new runs' handcrafted block is 74 (68 core + min/max features, plus the 6 pad/flank-derived), with the one-hot side at 609. Non-PC totals coincide at 683, so the label "handcrafted_sparse" likely denotes different feature compositions in `results/tables/slot` versus these JSONs (52+631 vs 74+609). The baseline JSONs are not committed, so composition cannot be verified from git. If thesis comparisons pair these runs against the 2026-09-26 baselines, this needs confirming.
Severity: risk (presentation). Evidence: TSV rows vs JSON `config.feature_names` (5b1a215).
