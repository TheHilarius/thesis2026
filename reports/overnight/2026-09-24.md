# Thesis Overnight — 2026-09-24

## Summary

ESM-C fixed-29 window embeddings are now fully wired into the pipeline: four pad modes (zeropad, padtoken, impute_boundary, impute_bos_eos) added to config, modelling, and the matrix runner. A bug in ESM-C pad-token mode was fixed — it was silently identical to zero-pad at pad slots. ESM-IF was upgraded from 3 pad modes to 4 (eosrepeat replaced by boundary + eos_bos_repeat), aligning both toolkits for mode-for-mode comparison. The AlphaFold supplement fallback was removed from the ESM-IF script, the submit script was fixed, and 216 old log files were cleaned up (~334k lines). PCA variance analysis was rewritten to stream per-residue window embeddings instead of fitting on mean-pooled context vectors.

## Code Review — Shortcomings & Issues

**1. ESM-IF window modes missing from FEATURE_COMPONENTS and FEATURE_SETS**
`config.py:309-314` — `esmif_win` covers only `esmif_zero`. The three new ESM-IF modes (`esmif_pad`, `esmif_boundary`, `esmif_eos_bos_repeat`) have no FEATURE_COMPONENTS entries and no FEATURE_SETS entries. ESM-C got all 4 modes wired into both dicts. This means the pipeline's normal feature-set resolution path won't find ESM-IF pad/boundary/eos_bos_repeat for modelling — they can only be used via explicit --pca-sweep or ad-hoc invocations. If ESM-IF pad-mode ablation is planned, these entries are needed.
Severity: risk. Commit: 958ac26.

**2. Zero-byte log files committed (twice)**
`logs/04_modelling_esmc_win_zeropad_pca9_log_20260923_133704.txt` (ca95630, 0 bytes) and `logs/04_modelling_rf_handcrafted_sparse_esmc_win_zeropad_pca148_log_20260924_051542.txt` (3f984de, 0 bytes). These are SLURM output files that contain nothing — the jobs either haven't run or failed silently. Previously flagged; recurred in this range.
Severity: maintainability.

**3. ESM-C padtoken embeddings need re-generation**
The pad-token bugfix (b9cef87) changed what gets written at pad slots. The existing `esmc_context_embeddings_padtoken.h5` was generated with the old (broken) code, where pad slots were zeroed. The 03b_run_matrix.py default keys include `esmc_win_padtoken`, but running it against the old H5 will use incorrect pad-token embeddings. The SLURM script (run_matrix_esmc_windows_slurm.sh) correctly defers pad-token ("pad-token deferred"), but any existing prepared H5 or modelling results using the old padtoken data are invalid.
Severity: risk. Commit: b9cef87.

**4. `status=1` is now unused but still allocated in ESM-IF status array**
`embed_windows_esmif.py:444` — `statuses` uses int8 with legend "0=primary 1=unused 2=missing 3=notfound". Code 1 is dead after removing the AF2 fallback. The inspect script (inspect_window_embeddings.py:323-325) checks for `fallback_flag` when `status` is absent. Keeping the unused slot is harmless but adds a confusing legend entry.
Severity: style. Commit: c5b0a3e.

**5. `run_matrix_esmc_windows_slurm.sh` references `04b_run_matrix.py`**
The SLURM script calls `04b_run_matrix.py` (not `04_modelling.py`). This appears to be a separate script for the matrix-run workflow. The script name is not visible in the diff context — worth confirming it exists and is current.
Severity: style. Commit: b1832f6.
